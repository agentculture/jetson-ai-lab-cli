# jlab discord paged read + regex search

> jlab discord reads a channel's full history past the 100-message cap and filters it with a regex
> instruction: the end-to-end demonstration is the motivating case: fetch a public channel whose recent 100 messages stop short of September, then search it for a September-dated pattern and get a hit

## Audience

- Jetson AI Lab maintainers and the jetson-ai-lab-cli agent itself, who need to read what was actually said in a public channel — not just how much was said (active) or what was linked (links)

## Before → After

- Before: jlab discord read shows at most the 100 most recent messages of one channel and offers no way to filter them; anything older is reachable only as a count (active) or a URL (links), never as text, so a maintainer asking 'what did people say about X in September' has no command to run
- After: jlab fetches a public channel's history backwards past the 100-message ceiling into a local MongoDB cache, fetching only what is missing on a repeat run, and serves read and regex-search as repeatable queries over that cache — so a suspect hit can be followed by a narrower read or a deeper dive without re-hitting Discord

## Why it matters

- this is the missing half of the agent's stated purpose: CLAUDE.md says the agent can read the Discord today but does not yet index sources or answer questions, and every indexing or answering path downstream needs message bodies over an arbitrary window as its input

## Decisions

- regex execution gets a defence: either an in-process guard or running the match inside a bounded sandbox such as the sibling headspace-cli, whose Policy model already ships closed-by-default budgets — `cpu_limit`, `wall_clock_seconds`, memory, pids and concurrency, with network DISABLED by default (headspace/core/policy.py:50-98)
- the cost of re-reading a window to detect deletions is accepted and is not a reason to weaken the sweep: re-reading is a loop of code and cheap, while failing to respect a member's privacy is expensive — so the sweep's frequency and completeness are set by the privacy obligation, never trimmed to save requests
- discord read serves from the Mongo cache, which the daily sweep keeps current, and gains a --refresh flag that forces a re-read from Discord when something may have been added or changed — so the cache is the default source of truth for read and the live path becomes explicit rather than implicit

## Hard questions

- how much message body does a match surface and where does it persist — the matching line only, the whole message, or a context window; and is the output stdout/JSON only (like read/channels/active) or a per-run gitignored HTML+CSV artifact set (like members/links)? (resolved: full message bodies are retained deliberately: the user approves extending message retrieval and has used this token to back up channel content before, so the Mongo cache holds complete messages and the reports render matched bodies — the members no-content rule is explicitly not inherited here)
- does the mongo cache ship as a second optional extra (\[mongo\], lazy-imported like discord-bot-cli, core install stays deps=\[\]) with a degraded no-cache path when it is absent, or does jlab take pymongo as a hard runtime dependency and abandon the deps=\[\] rule? (resolved: pymongo ships as a hard runtime dependency; the zero-runtime-dependency rule is retired and CLAUDE.md's Conventions section is rewritten accordingly — no \[mongo\] extra, no degraded no-cache path)
- which instance and database does jlab write to — qq-mongodb on 27017, a jlab-owned database inside eidetic-mongo on 27018, or a new container — and is this Discord corpus meant to feed eidetic-cli#3's memory layer later or stay a separate private cache? (resolved: jlab writes to its own database on eidetic-mongo (27018))
- does coverage become a list of intervals per channel (merged on overlap) rather than a single oldest/newest pair, and does a search over a window with an interior gap say so rather than presenting partial results as complete? (resolved: approved: coverage is stored as a list of intervals per channel, merged when they overlap or touch, so 'what is missing' is real interval arithmetic; a search over a window with an interior gap says so rather than presenting partial results as complete, and an interrupted fetch narrows coverage instead of widening it)
- does a fetch re-verify the public flag of channels it already holds and evict content for any that is no longer public, or does the cache keep serving what was public when it was captured? (resolved: a channel that becomes private has its cached content purged by the daily reconciliation sweep; 'public at capture time' is not the accepted posture — visibility is re-verified on a schedule and content follows the channel's current state)
- what is the retention position: does the cache carry a TTL or pruning policy, does a refetch reconcile deletions and edits against what is stored, and is there a documented way to purge a channel or an author's content on request? (resolved: settled by Discord's Developer Terms as the user researched them: deletion is required on user request, on Discord request, and when retention is no longer necessary for the stated functionality; encryption at rest is separately required; and a privacy policy covering collection, storage, retention, sharing and deletion must be linked in the Developer Portal — captured as c40, c41, c42)
- contradiction with c28? (resolved: read serves from the cache; the byte-identical-to-today obligation is restated rather than kept unconditional, because the cache — not a live fetch — is now read's default source)
- does read stay live-by-default and gain an explicit --cached flag, or does it serve from cache and fall through to a live fetch when the window is not covered — and if it falls through, is the byte-identical obligation restated as 'same output when the cache is cold' rather than unconditionally? (resolved: --refresh is the explicit escape hatch that forces a live re-read; there is no implicit fallback that silently hits Discord)
- are the jetson-bot `TERMS_OF_SERVICE.md` and `PRIVACY_POLICY.md` the documents that cover this agent, to be rewritten there — and does the 'free copying and distribution' promise get removed, since it contradicts deletion on request? (resolved: resolved by the 2026-09-12 rewrite: the jetson-bot `TERMS_OF_SERVICE.md` and `PRIVACY_POLICY.md` are the covering documents, they now describe collection, storage, retention, sharing and deletion, and the free-copying-and-redistribution promise has been removed and replaced with an explicit non-redistribution statement)
