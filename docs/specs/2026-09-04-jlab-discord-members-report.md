# jlab discord members report

> jetson-ai-lab-cli can now generate a report of the most active members of the Jetson AI Lab Discord, so Channel Maintainers can expand outreach looking for presenters.
> instruction: Ship as a new 'members' verb in the existing discord noun group (jlab/cli/`_commands`/discord.py + jlab/cli/`_discord.py`), following the repo recipe: register(sub), a `cmd_`\* handler, --json, CliError on failure, an explain catalog entry for ('discord','members'), and tests. Stage it scan -> aggregate (ids only) -> translate -> render so c16/h25 hold structurally. Verify with 'uv run teken cli doctor . --strict' plus the lint set.

## Audience

- Jetson AI Lab Discord Channel Maintainers, who need to find community members worth approaching as presenters — plus the humans and agents who read the generated report to do that judging.
  - instruction: Validate by handing a generated report to a maintainer cold, with no walkthrough.

## Before → After

- Before: Maintainers have no view of who is active. 'jlab discord active' ranks channels by traffic but never touches author identity, so there is no way to see which PEOPLE are participating. Finding presenter candidates means scrolling Discord by hand across ~100 public channels.
  - instruction: Re-check jlab/cli/`_discord.py`::`active_scan` before claiming the gap still exists.
- After: A maintainer runs one jlab command and gets a gitignored HTML report, openable in Chrome, containing overall statistics and diagrams about member participation in the guild's public channels — message counts, breadth across channels, thread/question starts, and substance signals — organized so a human or agent can read it and decide who to approach.
  - instruction: The verb writes the HTML and prints its path; --json emits the same statistics structurally.

## Why it matters

- Presenter outreach is currently guesswork limited to whoever a maintainer already happens to notice. Organized participation statistics widen the candidate pool to people who are genuinely active but not already visible to the maintainers.
  - instruction: Compare the report's members against the maintainers' existing candidate list on the first real run.

## Requirements

- The seam work is DELEGATED upstream and is NOT a blocker: open a GitHub issue on agentculture/discord-bot-cli (via 'agtag issue post') requesting author.bot, a recognizable display name, and after/time-window pagination past the 100-message cap in channel.py::`_message_dict` and the messages verb, so their agent picks it up, PRs and releases it. Meanwhile jlab implements those three itself against the raw discord.py objects its action closures already hold (the documented scripts/channels.py library-reuse pattern), so jlab work proceeds in parallel and drops its local workaround once upstream ships. Separately, jlab installs the \[discord\] extra into its own venv so 'uv run jlab discord doctor' passes and the members verb is verifiable end-to-end from this repo.
  - instruction: Keep the local bot/display-name/paging workaround isolated in jlab/cli/`_discord.py` so v5's cleanup is a single-file change.
  - honesty: jlab's local implementation is written so it can be REPLACED by the upstream fields when issue #14 ships, rather than becoming a permanent fork of the seam.
- API cost is approved: the members scan may page ~100 public text channels across the full time window without cost-driven truncation. Default window 90 days, overridable via --since.
  - instruction: Measure a real 90-day run over the guild's public text channels and record the wall-clock figure.
  - honesty: A channel whose full window could not be paged is reported as incomplete rather than silently truncated, so the statistics never overstate their own coverage.
  - honesty: A full-window run completes in a time a maintainer will actually wait for, and its runtime is stated up front rather than discovered.
- The scan must bound its concurrency. `active_scan`() today does asyncio.gather over EVERY public text channel with no cap (jlab/cli/`_discord.py`:238) — 104 channels in the live guild. Under c15's full-window paging each channel becomes many paginated requests, so an uncapped gather puts hundreds of requests in flight at once and will hit Discord rate limits. Bound in-flight channel reads (a semaphore) and handle 429 backoff explicitly.
  - instruction: Bound `_probe_channel` fan-out with an asyncio.Semaphore; make the cap a flag with a conservative default. Verify against the live 104-channel guild.
  - honesty: A full-window run completes without hitting Discord rate limits, and if it is throttled it degrades gracefully rather than producing silently partial data.
- A channel that FAILS to read must be distinguishable from a channel with no messages. `_probe_channel`() (jlab/cli/`_discord.py`:195-200) catches every exception and returns an empty message list, so a permissions error, a 429, or a transient failure silently contributes zero messages. Under a members report that understates real people's activity with no signal, and it directly contradicts h8's promise that incomplete coverage is reported rather than silently truncated.
  - instruction: Replace the bare 'except Exception: msgs = \[\]' with a per-channel status (ok / partial / failed + reason) carried through aggregation into the report. Do not widen the swallow to the members path.
  - honesty: The report distinguishes 'this channel had no activity' from 'this channel could not be read', and a reader can tell which happened.
- The report must carry run metadata on its face: scan timestamp, window start/end, channels attempted, channels fully covered, channels that failed or were rate-limited. Without it h8 and h20 are unverifiable by the reader, and there is no way to tell a quiet month from a broken run.
  - instruction: Render the run metadata block in the HTML header and include it in --json.
  - honesty: Someone reading the report months later can tell when it was generated, what window it covers, and what it failed to cover — without re-running it.
- The report's output path is fixed inside this repository (and gitignored there), or the command refuses to write. c9/h18 rely on .gitignore for containment, but .gitignore only protects THIS repo — a default of the current working directory means running the verb from another checkout writes person-level data into a repo with no such ignore rule, silently defeating c9.
  - instruction: Resolve the output path relative to the repo root (as whoami.py locates culture.yaml, walking up from `__file__`), not the CWD; refuse rather than write elsewhere.
  - honesty: Running the verb from an unrelated directory cannot write person-level data outside this repo's ignored output path.
- Member display names are attacker-controlled strings and must be HTML-escaped where the report renders them. A Discord username or `global_name` can contain markup; injecting it unescaped into the generated page is a script-injection vector in an artifact maintainers open in Chrome. Applies to any user-derived string reaching the HTML, not just names.
  - instruction: Escape every user-derived string at render (html.escape from the stdlib — no dependency). Add a test with a hostile display name.
  - honesty: A member whose display name contains markup renders as literal text in the report, and executes nothing.
- The --json output carries the same person-level data as the report and must be covered by the same containment rule as c21. c21 fixes the HTML report's path, but every jlab verb supports --json to stdout (rubric requirement), so 'jlab discord members --json > /some/other/repo/out.json' writes ranked, name-resolved member data anywhere the caller likes, entirely outside c9's gitignore and c21's fixed path. Either --json stays id-only (no name resolution), or it inherits the same containment and warning as the report.
  - instruction: Simplest satisfying option: keep --json id-only and resolve names solely in the rendered report. If names must appear in --json, gate it behind an explicit flag that prints a containment warning to stderr.
  - honesty: A maintainer cannot obtain name-resolved member data outside the contained path without a deliberate, visible act.
- c18's fix must not silently change the existing 'discord active' verb. `_probe_channel` (jlab/cli/`_discord.py`:189) is called from exactly one place — `active_scan`:238 — so replacing its bare-except-returns-empty behaviour with a per-channel status changes 'active' too. The existing tests cannot catch it: tests/`test_discord.py` stubs jlab.cli.`_discord`.`active_scan` wholesale (lines 258, 285), so nothing exercises `_probe_channel`'s actual contract. Either version the seam for the members path or update 'active' deliberately, with tests that reach `_probe_channel`.
  - instruction: Add a direct test for `_probe_channel` (not via a stubbed `active_scan`) before altering it, so the existing behaviour is pinned first.
  - honesty: After the change, 'jlab discord active' behaves as it did before, or its change is deliberate and covered by a test that actually exercises `_probe_channel`.
- The members verb must register an explain-catalog entry at ('discord','members') and keep the discord noun's overview listing current. jlab/explain/catalog.py:222-227 registers one key per discord verb, and tests/`test_cli.py`::`test_every_catalog_path_resolves` asserts every registered path resolves — a new verb without a catalog entry fails CI, and 'teken cli doctor . --strict' enforces the same rubric rule.
  - instruction: Add the ('discord','members') catalog entry in the same commit as the verb; run the rubric gate locally before opening the PR.
  - honesty: 'uv run teken cli doctor . --strict' and the full pytest suite both pass with the new verb registered.
- The HTML rendering code must ship with tests that keep total coverage at or above the CI gate. pyproject.toml sets `fail_under` = 60 (line 52); an HTML+SVG renderer is a large block of mostly-string-building code, and adding it untested can drop the project under the gate and fail CI on an otherwise correct PR.
  - instruction: Run 'uv run pytest -n auto --cov=jlab --cov-report=term' and record the number before the PR.
  - honesty: Coverage after the ship is at or above 60, measured — not assumed.
- Authors who have left the guild are excluded from the report by default, with an explicit flag to include every author regardless of current membership. The membership check uses guild.`fetch_member` (verified working under the existing read-only token) and runs inside the same batched translation session as name resolution, so it costs no extra pass. Departed authors are counted in coverage totals but omitted from the member statistics, and the report states how many were excluded.
  - instruction: Resolve membership in the same session as the id->name batch (t4). Prefer the per-guild nick as the display name, falling back to `global_name` then username.
  - honesty: A maintainer is never handed an outreach candidate who has already left the guild, unless they explicitly asked to include everyone.

## Honesty conditions

- The report is generated from public channels only, verified by the same @everyone `view_channel` check `list_channels`() already uses — no private-channel message contributes to any member's statistics.
- The scan actually covers a stated time window (e.g. last 30/90 days) rather than just the last N messages per channel — which requires adding 'after'-based pagination to `read_messages`(), since today's 1..100 cap silently truncates busy channels.
- Bot and webhook authors are excluded, which requires serializing author.bot at the adapter seam — it is not serialized today.
- The generated HTML opens and renders its diagrams in Chrome from the local filesystem, with no build step and no Python charting dependency added.
- The report output path is gitignored, so running the command cannot accidentally commit person-level data.
- The word 'report' does not imply a verdict: the output presents statistics and diagrams, and nowhere labels a person as 'most active' or recommends them as a presenter.
- The intermediate scan/aggregation data contains no usernames — only author ids — so an unrendered run leaks no identities.
- jlab's own venv has the \[discord\] extra installed, so 'uv run jlab discord doctor' exits 0 (not today's exit 2) and the members verb runs from this repo rather than only from the sibling checkout.
- The report is actually usable by a Channel Maintainer without reading Python or JSON — it opens in Chrome and reads as statistics, not as a data dump.
- 'jlab discord active' genuinely offers no per-person view today — verified: it aggregates `msgs_in_window` per channel and never reads author identity.
- It is ONE command, not a pipeline the maintainer has to assemble: a single jlab invocation produces the finished HTML file.
- The report surfaces at least some active members who are NOT already known to the maintainers — otherwise it only confirms what they knew and widens nothing.
- No output field, column header, sort order, or diagram title implies a verdict — a default sort is presentation, not a recommendation, and must be labelled as such.
- Public-channel filtering happens BEFORE any message is read, not as a post-filter on collected data, so private content never enters the process at all.
- The added code paths contain no Discord write call of any kind.
- The output path is in .gitignore BEFORE the first report is generated, so no run can ever stage person-level data.
- pyproject.toml's 'dependencies = \[\]' is unchanged by this ship, and the generated HTML renders its diagrams offline or from an allowed CDN without a build step.
- The report states its own coverage — it says on its face that it covers text channels only, so a reader never mistakes it for whole-guild coverage.
- Bot exclusion uses the authoritative author.bot flag, not a name heuristic or a hand-maintained denylist.
- The maintainers actually run it and say whether it surfaced anyone new — the signal is their feedback, not our assumption that it worked.
- Name resolution is a separate, final stage — the aggregation output can be inspected on its own and contains only ids.
- No member's words appear anywhere in the intermediate data or the report — inspecting either shows only counts, lengths, and ids.
- Text-authorship genuinely identifies presenter candidates — validated against maintainers' judgement on the first real run, not assumed.

## Success signals

- A Channel Maintainer opens the generated HTML in Chrome and, without opening Discord, can identify presenter candidates they had not previously considered — the report surfaces active members the maintainers were not already aware of.

## Scope / boundaries

- The CLI does NOT rank, score, judge, or recommend anyone. It emits no 'most active member' verdict and no presenter shortlist. It organizes statistics; humans and agents do the analysis.
  - instruction: Grep the rendered HTML for verdict language ('top', 'best', 'most active', 'recommended') before shipping.
- Public channels only. Per-member statistics are computed exclusively from channels the guild's @everyone role can `view_channel`; a private channel's participation must never reach a member's totals or the report.
  - instruction: Reuse the @everyone `view_channel` check from `list_channels`(); assert in a test that a private channel is never fetched.
- Read-only. No post, react, thread-create, DM, or any other write path is added — the members report only reads history, consistent with the existing discord noun group.
  - instruction: Grep the diff for send/edit/delete/`add_reaction`/`create_thread`; a test asserts the adapter exposes no write verb.
- Report output is gitignored and never committed. No person-level aggregation enters git history.
  - instruction: Add the ignore rule in the same commit that adds the verb, not after; assert with 'git check-ignore'.
- Zero runtime dependencies stays true: no Python charting or templating library is added. Diagrams are hand-emitted SVG or a CDN-loaded JS chart lib inside the generated HTML.
  - instruction: Assert dependencies == \[\] in a test; open the report with the network disabled to see what still renders.
- Phase 1 covers public TEXT channels only, matching `active_scan`'s existing type filter. Forum channels and threads are a follow-up slice, explicitly not promised in this ship.
  - instruction: Render the covered channel types and channel count into the report header.
- Bots and webhooks are excluded from all statistics; only human authors are counted.
  - instruction: Read m.author.bot off the raw discord.py object (available per s11); never pattern-match on username.
- The scan and aggregation stages are anonymous: they key on author.id only and never store or emit a username. Human-readable names enter only at the final batch translation step that renders the report.
  - instruction: Structure it as scan -> aggregate (ids only) -> translate -> render, with the id-only stage independently dumpable.
- Message CONTENT never leaves the aggregation stage. The 'substance' signal uses message LENGTH and reply counts — numeric derivatives — so no member's words are stored in intermediate data or quoted in the report. c16 protects usernames but says nothing about content; note `active_scan`'s existing 'preview' field (jlab/cli/`_discord.py`:180) does carry verbatim content, and the members path must not inherit it.
  - instruction: Compute length at read time and discard content immediately; do not reuse `_rank_channel`'s 'preview' field on the members path. Assert in a test that no message content reaches the aggregate.

## Assumptions

- The frame assumes text-message authorship is a usable proxy for the participation that predicts a good presenter. That assumption is unstated anywhere in the confirmed claims, and it is load-bearing for the whole report.
